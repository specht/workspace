Ein Webserver in Ruby oder Python, ohne Bibliothek, in sechs Schritten: zuhören, antworten, Pfade mit 404, Dateien ausliefern, Parameter und ein Zähler, ein Formular mit `POST`. Die Aktivität schließt an TCP/IP an und macht sichtbar, was Live Server, Sinatra oder nginx tun. Vorausgesetzt werden Grundlagen in Ruby oder Python (Variablen, Schleifen, Funktionen, Verzweigungen) und die Seite TCP/IP. Welche Sprache eine Klasse sieht, stellst du auf der [Klassenseite](/klasse) unter »Sprache« ein, ohne Einstellung ist es Ruby. Lernende können auf der Seite selbst umschalten; eine Aufgabe, die sie in einer Sprache gelöst haben, gilt auch in der anderen. Die ausgelieferten Seiten in <code>public</code> sind in beiden Sprachen dieselben.

**Was schiefgeht.** »Address already in use« heißt: Ein alter Server läuft noch, oft im anderen Terminal. <kbd>Strg</kbd><kbd>C</kbd> dort beendet ihn. Nach jeder Änderung muss der Server neu gestartet werden; ein Server, der nicht neu gestartet wurde, ist die häufigste Ursache für »es ändert sich nichts«. Fehlt die leere Zeile `"\r\n"` nach den Headern oder stimmt `Content-Length` nicht (Zeichen statt Bytes bei Umlauten), wartet der Browser oder schneidet ab. Ausgaben mit `puts` oder `print` erscheinen im Terminal des Servers, nicht im Browser. Liest der Server den Body zeilenweise (`client.gets` in Ruby, `reader.readline()` in Python) statt mit `read`, hängen Server und Browser: Hinter dem Body steht kein Zeilenumbruch. In Python sind Antworten Bytes: Ein `str` an `sendall` ergibt einen `TypeError`, darum gehört `encode()` davor.

**Die Aufgaben.** »Die erste Antwort« liest `server.rb` und sucht Status-Line, `Content-Length` und `Thread.new` (in Python `server.py` mit `threading.Thread`); »Eine Seite aus public« prüft `public/index.html`. »Dein Server grüßt« führt den `curl`-Befehl der Lernenden in ihrem Workspace aus (als Gast, ohne Schreibrechte) und prüft, was ihr laufender Server auf `/hello?name=Ada%20Lovelace` antwortet; läuft der Server nicht, kommt keine Ausgabe. Die übrigen fragen nach Request-Line, Bytes, Statuscodes, der Sicherheitsprüfung, dem Mutex und dem Body; »Eine Seite, die es nicht gibt«, »Ein Name in der Adresse« und »Neu laden« sind Vorhersagen. »Eine Umfrage« sucht in `server.rb` nach `POST`, `Content-Length`, `client.read` und `303`, in `server.py` statt `client.read` nach `reader.read`.

**Jetzt bist du dran.** Ab den Dateien aus `public` zeigt die Seite nur noch, was sich am Server ändert, mit grauen Zeilen drumherum, statt die ganze Datei noch einmal. An drei Stellen schreiben die Lernenden den Code zuerst selbst: die Auswahl, die alles außer `/time` an `serve_file` gibt, den Fall `/hello` und die Funktion `redirect`. Wer den Überblick über die eigene Datei verliert, findet jede Stufe vollständig unter `stufen/`. Vor dem Code der Seite stehen zwei Tipps, ein Denkanstoß und ein Gerüst mit Lücken. Der zweite erscheint erst eine Minute, nachdem der erste aufgeklappt wurde, und der Code der Seite (»Lösung anzeigen«) eine Minute nach dem zweiten; eine Uhr zeigt die Seite nicht, damit die Lernenden mit dem Tipp arbeiten, statt auf den nächsten zu warten. Die Seite geht danach mit diesem Code weiter. Wer welchen Tipp aufgeklappt hat, sieht niemand außer der Person selbst. Den Fall `/hello` prüft »Dein Server grüßt« am laufenden Server; wer sie löst, kann den Code der Seite sofort öffnen.

**Weiter.** Die Pixelwand baut auf diesem Server auf und ergänzt WebSockets. Für ein Gespräch über Sicherheit eignet sich die Prüfung mit `start_with?` (Python: `startswith`): Die Seite lässt den Angriff mit `curl --path-as-is localhost:8000/../server.rb` (oder `server.py`) ausprobieren, einmal mit und einmal ohne die Prüfung; ohne sie liefert der Server seinen Quelltext aus. Browser und normales `curl` entfernen `..` selbst, darum fällt die Lücke beim bloßen Klicken nicht auf.
