Die ganze Klasse malt an einem Bild, live: ein Server in Ruby oder Python mit WebSockets in drei Schritten (Echo, Nachrichten an alle, die Pixelwand), dazu eine kleine Webseite mit `<canvas>`. Handshake und Frames übernimmt eine Bibliothek, in Ruby faye-websocket, in Python das Paket websockets; die Lernenden kümmern sich um Verbindungen, Verteilen, JSON und das Prüfen fremder Nachrichten. Am Ende gibt eine Person (oder die Lehrkraft) Port 8000 frei, und alle malen gemeinsam. Ein letzter Abschnitt zeigt an einem Zähler, was Threads ohne Lock anrichten. Vorausgesetzt wird »Ein eigener Webserver«. Welche Sprache eine Klasse sieht, stellst du auf der [Klassenseite](/klasse) unter »Sprache« ein, ohne Einstellung ist es Ruby. Lernende können auf der Seite selbst umschalten; eine Aufgabe, die sie in einer Sprache gelöst haben, gilt auch in der anderen.

**Was schiefgeht.** Fehlen die Gems, bricht `ruby server.rb` mit `cannot load such file -- faye/websocket` ab. In Python heißt `ModuleNotFoundError: No module named 'websockets'` fast immer: Der Server wurde mit `python3` statt mit `.venv/bin/python` gestartet. Ein `pip install` ohne Umgebung lehnt das System ab (»externally-managed-environment«). Schließt ein Programm die Verbindung ohne Abschied, wie `curl` beim Handshake, zeigt der Python-Server einen `ConnectionClosedError`; das ist harmlos, der Server läuft weiter. Nach jeder Änderung den Server neu starten und die Seite neu laden. Läuft kein Server, zeigt die Browserkonsole (<kbd>F12</kbd>) »WebSocket connection failed«.

**Viele Threads.** `flood.js` schickt 200 Pixel an den eigenen Server auf `localhost`. Vier Threads arbeiten eine Warteschlange ab (eine feste Zahl, denn Workspaces begrenzen die Zahl der Threads; ein Thread pro Nachricht scheitert dort bei etwa 160). Ohne Lock steht der Zähler danach weit unter 200, im Test bei 58, weil die Threads denselben alten Wert lesen, während einer speichert; mit `$lock.synchronize` bei 200. Faye selbst ruft die `on`-Blöcke nacheinander in einem Thread auf, darum brauchen die ersten Stufen keinen Lock. In Python hat jede Verbindung ihren eigenen Thread; die Menge `clients` kommt trotzdem ohne Lock aus, weil `add` und `discard` einzelne Schritte sind und `broadcast` über eine Kopie geht. Ohne Lock kommt der Python-Server im Test bei 89 an. Das Skript erreicht nur den eigenen Server: Shared Live Apps lassen nur angemeldete Browser herein, und Workspaces erreichen einander nicht direkt. Die Seite sagt deutlich, dass das Überschütten fremder Server ein Angriff ist (§ 303b StGB); wer eine geteilte Wand schützen will, baut die Wartezeit pro Verbindung aus den Ideen.

**Die Aufgaben.** »Die Pixelwand« liest `server.rb` und sucht `JSON.parse`, `Faye::WebSocket` und eine Bereichsprüfung, »Ein Lock« `Thread.new`, `Mutex.new` und `synchronize`; in Python lesen sie `server.py` und suchen `json.loads`, `websockets` und eine Bereichsprüfung, `threading.Thread`, `Lock()` und `with lock`. Die Abgabe lässt den Ordner `.venv` aus. Die übrigen fragen nach dem Statuscode 101, wer eine Nachricht bekommt und was der Zähler nach 200 Pixeln zeigt (Vorhersagen), der Größe des Bildes und warum ein Server fremden Nachrichten nicht trauen darf.

**Weiter.** Die Ideen am Ende der Seite, vor allem die Wartezeit pro Verbindung (wie »r/place«), entstehen meist von selbst, sobald die ersten das Bild übermalen.
